# 5-1 アカウント種別・権限の整理（2026-10-25）

初回公開は**個人アカウントでの利用**に限定する。グループのDB構造は将来用の下地として残すが、グループの選択・共同編集・招待を公開機能として案内しない。これはユーザーの進捗表でグループ実装（1-12/2-12）がP3であること、現行のWeb/iOSとRLSが個人の単一`account_id`を中心に動くことに基づく公開範囲の提案である。料金・件数など無料プランの境界は5-4で決める。

## 現在の実装

| 層 | 個人アカウント | グループに関する下地と限界 |
| --- | --- | --- |
| DB・認証 | 新規Authユーザーには個人`accounts`、`public.users`、有効な`owner`所属、`free`契約が生成される。`routes`・`runs`・写真・Storageは本人の`account_id`を中心にRLSで保護し、2ユーザー＋匿名試験で越境書き込みを拒否した。 | `accounts.type`は`user`/`org`、`account_memberships.role`は`owner`/`admin`/`editor`/`viewer`を保存できる。所属とプラン権利はログインユーザーに読み取りのみ許可。だがルート・実走の操作権限はロール別の共同所有モデルへ移行していない。旧`owner_account_id`も権限判定の中心ではない。 |
| Web | `AccountProvider`は所属・契約を読み、個人アカウントを優先して選ぶ。ルート・実走、GPX取込、公開設定、写真操作を提供する。現在の一般ユーザーの書き込みはDB側の本人境界で制限される。 | 複数所属があればアカウント切替を表示する。`permissions.ts`にロール順位の補助関数はあるが、画面の編集・公開・削除操作には使用されていない。グループを選べても、個人`account_id`を使う現行RLSでは共同編集の動作を保証できない。 |
| iOS | `users.account_id`を1件取得し、保存済みルート、走行履歴、走行同期に使用する。開発版Webとの読み書き共有を確認済み。 | 複数所属の選択やグループロールの参照・強制はない。個人の実走記録をグループへ直接保存する経路もない。 |

根拠: `docs/schema-baseline-rollout-20261016.md`、`docs/rls-two-user-audit-20261013.md`、`docs/legacy-policy-cleanup-20261018.md`、`docs/web-functional-smoke-test-20261018.md`、`src/features/accounts/{api,AccountProvider,permissions}.ts(x)`、`src/app/AppLayout.tsx`、iOSの`src/lib/{saved-routes,run-history,ride-sync}.ts`。古い`docs/current-database-inventory.md`の「開発者限定RLS」等は2026-10-12以前の記述なので、後日の適用・試験記録を優先する。

## 初回公開に必要な権限境界

| 主体 | 許す操作 | 許さない操作 |
| --- | --- | --- |
| 匿名 | 公開ルートと、プライバシー除外に該当しない公開マーカー・写真の閲覧 | 非公開ルート・実走の閲覧、記録作成、プロフィール・所属情報の取得 |
| ログイン済み個人本人（`active/owner`） | 自分のプロフィール、非公開ルート、実走、写真の閲覧・作成・更新・削除。自分のルートの公開・非公開切替。空の個人アカウントの退会 | 他人の非公開データの閲覧・編集・削除、他人のアカウントIDを指定した保存や公開 |
| 別のログインユーザー | 自分の個人データと、他人が公開したルート・除外されない写真の閲覧 | 他人のルート・実走・写真の変更、他人の所属の利用 |

初回公開では画面とAPIの対象アカウントを**本人の個人アカウントに固定**する。既存の`account_memberships`や`plans`のスキーマを削除する必要はない。グループアカウントが既に存在する／後から付与される場合でも、未対応のグループ選択を画面に出さない公開ガードが必要である。`permissions.ts`のロール順位だけを画面に適用して共同編集を有効化してはならない。DBのRLS・RPC・StorageとiOSの対象選択を同時に設計する必要がある。

## 5-1を完了にする前の実装・確認

1. Webで初回公開時のアカウント切替を個人だけに制限し、ルート作成・GPX取込・マイページの対象が本人の個人`account_id`であることを確認する。グループの選択肢や作成・招待・管理導線は公開しない。**実装済み:** `getAvailableAccounts()`が本人の個人ID・`owner`所属だけを返し、グループを返さない。旧式の個人アカウントだけがある場合の互換経路は維持。グループしかない利用者や同じ個人IDに非owner/組織レコードがある場合は0件で止める。境界テスト4件、lint、開発ビルドは通過。開発Pagesへの配信後の画面確認は別途記録する。
2. 新規登録で個人アカウント、`active/owner`所属、`free`契約が作られ、ログアウト・再ログイン後も同じ個人アカウントが選ばれることを確認する。既存ユーザーの所属欠落件数も0であることを照合する。
3. 2ユーザー＋匿名のRLS試験を現在のDB状態で再確認し、本人のCRUD・公開RPC成功、他人の非公開閲覧と変更の拒否、プライバシー除外を確かめる。iOSでの個人ルート・走行の表示／同期は既存の実測記録を基礎にする。
4. 個人以外のアカウントに所属するテストユーザーでも、公開UIからグループを操作できないことを確認する。グループ用の共有編集権限はこのリリースの完了条件に含めない。

## グループ機能として後から追加するもの

- 招待・承諾・脱退、所属状態の遷移、`owner`/`admin`/`editor`/`viewer`の操作表と所有権移譲。
- グループのアカウント切替、共有ルートの作成・編集・公開・削除、写真の権利とStorageパス、個人実走からの掲載選択。
- `owner_account_id`を含むデータ所有の統一、ロールを反映したRLS・RPC・Storageポリシー、Web/iOS双方の権限表示と2ユーザー以上の境界試験。
- グループプランの機能・上限・課金。5-4の個人無料プランとは分けて決める。

**判定:** 5-1の現状整理と初回公開範囲の提案、Webの公開ガードの実装はできた。開発Pagesへの配信後の個人利用画面確認、既存の2ユーザー・匿名RLS境界の現行DBとの再照合、グループ所属ユーザーでの画面確認が残るため、5-1全体はまだ完了扱いにしない。本番DB・開発DB・iOSアプリへの変更は行っていない。
